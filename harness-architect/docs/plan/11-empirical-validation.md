# Phase 11 — 경험적 검증 (프롬프트 eval → 품질 측정)

> 설계: 리졸버의 **구조적** 검증(참조·충돌·예산·권한)을 넘어, "이 하네스가 모델 출력을
> **실제로 낫게 하는가**" 를 측정하는 레이어. Phase 2 러너 + Phase 10 프롬프트 IR 위에 얹고,
> 신호를 Phase 9 피드백 루프로 되먹인다.

## 왜 (차별화이자 신뢰도)

우리의 정체성은 **"그라운딩된 추천"** 이다. 그런데 지금 검증은 100% 구조적이다 — 리졸버가
참조·충돌·예산·권한·훅 순서를 보증하고 pytest/골든 스냅샷이 코드를 지킨다. 하지만 **"추천된
하네스가 붙였을 때 결과가 좋아진다"** 는 증거는 하나도 없다. 그라운딩은 증거가 없으면 주장일
뿐이다.

인접 도구([revfactory/harness](https://github.com/revfactory/harness))의 가장 강한 무기는 바로
이 숫자다 — with/without 스킬 A/B 로 "평균 품질 +60%"(자가측정 n=15). 우리가 "카탈로그 근거"
를 팔면서 품질 델타를 못 보여주면 서사가 비게 된다.

부수 효과가 더 크다: eval 점수는 **카탈로그(=최우선 자산) 품질을 키우는 피드백 루프
([09](./09-feedback-and-catalog-lifecycle.md))의 실제 연료**가 된다. `retention_score` 는
"사용자가 **유지**했나" 지 "출력이 **좋아졌나**" 가 아니다 — eval 은 후자를 직접 잰다.

## 목표

카탈로그 컴포넌트·시나리오에 **eval 케이스(입력 → 기대 속성)** 를 첨부하고, 하네스를 붙인
구성과 안 붙인 구성을 같은 케이스로 돌려 **품질 델타(점수·토큰·지연)** 를 측정한다. 결과는
리포트로 내고 Phase 9 신호 파이프에 **품질 신호**로 흘려보낸다. 키 없으면 결정적 체크만 돌고
(로컬 폴백 불변), LLM-judge·live 측정은 키 있을 때 자동 활성.

## 작업

1. **Eval 케이스 스키마** — 카탈로그 컴포넌트/시나리오에 선택적 `evals:` 블록. 각 케이스는
   `input`(프롬프트/컨텍스트), `expect`(결정적 체크: `contains`/`not_contains`/`regex`/구조
   체크) + 선택적 `rubric`(LLM-judge 채점 기준). 스키마·로더는 카탈로그 규약(`schema/`)과 일관.
   결정적 체크를 1급으로 두고(재현성), judge 는 보조.
2. **Eval 러너** — `harness eval <harness.yaml>` CLI + `POST /eval`. `build_request`(Phase 10)
   → Anthropic 러너(Phase 2 재사용, `dry_run`/live) → 채점기(결정적 체크는 항상, LLM-judge 는
   키 있을 때). 클라이언트는 Phase 1·2 규약대로 **주입 가능**하게 두고 fake 로 코드 경로 테스트.
3. **Ablation / A-B** — 같은 eval 셋을 **with/without 특정 컴포넌트(또는 프롬프트 조각)** 두
   구성으로 돌려 델타 표(품질 점수 · `context_tokens` · 지연)를 낸다. "이 컴포넌트가 기여하는가"
   를 정량화 — 우리 카탈로그의 각 조각을 **경험적으로 정당화**하는 근거.
4. **리포트 + 피드백 연결** — eval 결과를 Phase 9 신호 파이프에 `quality` 신호로 emit(유지
   여부의 `retention` 과 별개 축). 컴포넌트의 최근 eval 점수를 카탈로그(화면 E)·대시보드(F)에
   표면화 → 추천 랭킹의 보조 신호 후보(별도 검토).
5. **시드 eval 셋** — 3 시나리오(PR 리뷰 · 이슈 분류 · 문서 초안)에 각 소수 케이스. 결정적
   체크 위주로 시작(예: 구조화 리뷰 포맷 준수, PII 미노출, 필수 섹션 존재), judge 는 이후 확장.

## 완료 기준

- [x] `evals:` 스키마 + 로더 + 검증 — `harness_runtime.eval` 의 `load_eval_file`·`load_eval_scenario`·
      `list_eval_scenarios`(CLI·API 공용). 같은 폴더의 `ranking-golden.yaml` 은 형식이 달라 거부한다.
- [x] `harness eval` CLI(+ `--scenario`) + `POST /eval` + `POST /harnesses/{id}/eval` +
      `GET /eval/scenarios`. 주입 가능 클라이언트 + fake 테스트는 기존대로.
- [x] Ablation — `harness ablate` (`--scenario` 도 지원).
- [x] 화면 노출 — 하네스 상세에 시나리오 셀렉터 + eval 버튼 + 결과 뷰.
- [x] 3 시나리오 시드 eval 셋 — `pr-review`·`issue-triage`·`doc-draft` 각 3케이스. 레시피 3종과 짝.
- [x] **키 없을 때 완주** — dry_run 이면 채점을 스킵하고 `mean_score: null` 을 돌린다(테스트로 고정).

## 구현 노트 (2026-09-07)

- **`mean_score: null` 은 0점이 아니다.** 키 없이 dry_run 이면 "잴 수 없었다"이고, 이걸 0 으로
  그리면 "품질이 나쁘다"로 읽혀 정반대 결론을 낳는다. UI 에서 `미채점 — 키 없이 dry_run` 으로
  구분해 표시하고 다음 행동(키 등록)을 알려준다.
- **빈 케이스는 422 로 거부한다.** `scenario`·`cases` 둘 다 없을 때 빈 리포트로 "통과"를 돌려주면
  검증했다는 착각을 만든다. CLI 도 같은 이유로 둘 중 하나를 요구한다.
- **로더를 코어로 올려 CLI 중복을 제거했다.** CLI 에 있던 `_load_cases` 가 API 에서 필요해졌고,
  두 곳에 같은 파싱을 두면 형식이 갈라진다(verify·preview·doctor 와 같은 결).
- **eval 셋은 "좋은 출력"이 아니라 재현 가능한 최소 계약을 고정한다.** 품질 판정은 사람·judge 의
  영역이고, 여기서 잡는 건 라벨을 말하는가·모르면 모른다고 하는가·비밀이 새지 않는가다.
  `doc-draft` 는 특히 **없는 사실을 지어내지 않는지**를 본다(초안이 오정보가 되는 걸 막는다).
- `/eval` 도 정책을 강제한다 — 같은 본문(`ResolveRequest`)을 쓰는 경로는 전부 지켜야 한다.

## 의존성

Phase 2 러너(완료) · Phase 10 프롬프트 IR/`build_request`(완료). Phase 9 피드백 루프와
**연동**(신호 소비처). 우선순위 P1 — 이식성(05) 다음의 신뢰도 축.

## 검증 한계

- **소표본·자가측정 편향** — 인접 도구도 "n=15, 저자 자가측정" 을 명시한다. 우리도 통계적
  유의성을 과장하지 않는다. 재현성을 위해 **결정적 체크를 1급**으로, LLM-judge 는 보조로 두고
  judge 프롬프트/모델을 리포트에 기록한다.
- **live 측정은 키 필요** — 키 없으면 결정적 체크만 돌고 judge/점수 델타는 스킵된다. 폴백
  경로는 절대 깨지 않는다.
- **품질 ≠ 프로덕션 성과** — eval 은 대리 지표다. 실사용 성과는 Phase 9 의 실사용 신호와
  합쳐 볼 때만 의미가 커진다.
