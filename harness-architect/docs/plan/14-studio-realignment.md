# Phase 14 — 스튜디오 재정렬 (그라운딩된 저작으로)

> 중간정리. 대화형 스튜디오가 추가되며 시스템의 무게중심이 **카탈로그-그라운딩 추천**에서
> **채팅-생성 저작**으로 이동했다. 원래 기획의 핵심 가치(발명 금지·실행가능성·살아있는 카탈로그)를
> 지키면서 더 나은 UX(대화형)를 얻으려면, 저작을 그라운딩의 *최후 단계*로 재편입해야 한다.

## 무엇이 드리프트했나 (그리고 무엇이 아닌가)

- **드리프트 아님 — 용어**: `harness = 에이전트의 선언 스펙`. eject 하면 `.claude/`·`.mcp.json`·
  `CLAUDE.md` = 실제 에이전트. "하네스 구성"과 "에이전트 구성"은 같은 출력이다.
- **진짜 드리프트 — 방법론·진실의 원천**:

  | | 원래 기획 (recommend) | 스튜디오 (author) |
  | --- | --- | --- |
  | 진실의 원천 | 카탈로그(실존 컴포넌트) | LLM 생성 |
  | 기본 동작 | 실존 추천 + gap 표시 | 설명 → 새 컴포넌트 초안 |
  | 핵심 가치 | 발명 금지(anti-invention) | draft-first(되묻지 말고 만들어라) |
  | 실패 모드와의 관계 | 이걸 *막으려던* 시스템 | …이게 *그 실패 모드* |

  아이러니: 원래 기획이 피하려던 "generic architecture generation"(카탈로그 근거 없이 그럴듯한
  컴포넌트 생성)이 스튜디오의 draft-first 저작과 구조적으로 같다. 관측된 증상: 실행이 필요한 능력
  (영상 편집 등)의 gap 을 hollow skill 로 "대체"해 덮음(skill=프롬프트라 실제 실행 못 함).

## 재정렬 원칙 — 추천과 저작은 한 파이프라인의 두 단계

1. **재사용 우선(그라운딩 추천)** — 실존 컴포넌트(2054+ 하베스트 MCP + 큐레이션)를 먼저 찾는다.
2. **gap 명시** — 카탈로그가 못 채우면 발명하지 말고 정직하게 gap.
3. **저작은 최후수단(그라운딩된)** — 진짜 gap 일 때만, ①실존 도구에 근거해 ②resolve 로 검증하고
   ③카탈로그로 피드백(다음 사용자의 gap 을 닫음).

즉 스튜디오는 "하네스 구성에서 벗어난 별개 시스템"이 아니라 **같은 그라운딩 시스템의 저작 팔(arm)**이다.

## 세 불변식 (앞으로의 가드레일)

1. **모든 컴포넌트는 실행가능해야 한다.** harness.yaml 로 내려가 실제로 돌아야 한다. 프롬프트(skill)로
   실행(MCP)을 대체 금지.
2. **발명보다 gap.** 못 채우면 정직하게 gap, 저작은 최후수단.
3. **저작은 카탈로그를 키운다.** 일회용이 아니라 피드백 루프로 다음 gap 을 닫는다.

## 작업

1. **재사용 우선 미션(가드레일 2)** — 스튜디오 미션 프롬프트를 draft-first 에서 reuse-first 로 재앵커:
   만들기 전에 `search_catalog` 로 실존을 찾고, 있으면 재사용, 없거나 gap 일 때만 draft. (허락은 안
   구하되 — 재사용 확인은 한다.) — **완료(orchestrator AGENT_SYSTEM).**
2. **조립 시 실행가능성 검증(가드레일 1)** — `assemble_harness` 가 조립된 에이전트를 resolve 해서
   gap/에러를 사용자에게 알린다(hollow 조립을 저장 전에 표면화). — **완료(orchestrator `_tool_assemble`).**
   앞서: 실존 도구 못 찾으면 gap 으로 남기기, hook 오용 검증(비-lifecycle provides), gap-aware 검색.
3. **저작 → 카탈로그 피드백(가드레일 3)** — 저작 컴포넌트가 재사용되게 검색에 편입. 전역 추천기는 유저
   무관 싱글턴(2054+ 1회 색인)이라 스코프별 재임베딩이 비싸므로, 유저의 **소수 ready 컴포넌트만 같은
   임베더로 즉석 점수화**(`Recommender.rank_components`)해 전역 결과와 병합하고 gap 을 전역∪유저 커버리지로
   재계산한다(`ScopedRecommender`). 스튜디오 검색·`get_catalog_item` 이 스코프 레지스트리를 봐서 저작
   컴포넌트를 찾아 재사용한다 → gap → 저작 → 재사용 → gap 닫힘. — **완료.**

## 완료 기준

- [x] 스튜디오 미션 reuse-first + 실행 대체 금지(gap 정직) + hook lifecycle 전용.
- [x] `assemble_harness` 가 resolve 로 gap/에러를 표면화(실행가능성 게이트).
- [x] 저작 컴포넌트가 스코프 격리 하에 추천 검색에 편입(`ScopedRecommender`, 피드백 루프).
- [x] 저작 컴포넌트를 **공유 카탈로그로 승격**(`promotion.py`, 리뷰 게이트: ready + validate). `POST
  /components/{cid}/promote` → origin='promoted'(신뢰등급 community)로 모든 유저 검색에 등장.
- [x] gap 수요 집계 → 저작 제안 연결: 인메모리 `GapDemand`(recommend·스튜디오 검색이 기록) + `GET
  /gaps/top`. 스튜디오 검색이 자주 요청되는(hot) gap 을 "★만들면 재사용됨"으로 우선 제안. durable 시딩
  집계는 `aggregate_gaps.py`(로그) 병행.

## 남은 것 (후속)

  추가 심사(CONTRIBUTING §3)는 배포 정책으로.
- `GapDemand` 는 프로세스-로컬(재시작 리셋). 크로스-레플리카·durable 수요는 DB 테이블로 승격 시 alembic
  마이그레이션 동반(후속).

## 검증 한계

가드레일 1·2 는 LLM 준수에 일부 의존한다(프롬프트가 주 레버). 결정적 부분: hook 오용은 resolver 가
하드 에러, 조립 gap 은 resolve 로 기계 판정. 저작이 "실행 필요 능력을 skill 로 눈속임"하는지는 여전히
LLM 판단 영역 — 피드백 루프(가드레일 3)와 실존 MCP 우선 추천이 근본 해법이다.
